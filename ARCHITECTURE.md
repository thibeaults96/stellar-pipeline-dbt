# Stellar Pipeline — Architecture Guide

Every file in the repo, what it does, and why it's here.

## How the system works

The game has three layers:

1. **dbt project** (`dbt_project/`) — a real dbt project with SQL models, YAML configs, CSV seed data, and snapshot definitions. When the player clicks "dbt run", actual dbt executes against a local DuckDB database.

2. **Game engine** (`stellar_dbt/`) — Python package that wraps dbt. Manages game state (objectives, XP, narratives), checks player work against real dbt artifacts and DuckDB query results, and fires story beats at the right moments.

3. **Web UI** (`frontend/`) — Next.js app with a Monaco code editor, objective panel, terminal output, DAG viewer, and a codec-style narrative panel. Talks to the game engine through a FastAPI server (`backend/`).

The player edits real `.sql` and `.yml` files. The game engine validates results by querying the actual DuckDB database — checking that columns exist with the right types and values, not by pattern-matching the SQL.

### `pyproject.toml`
Python package definition. Lists all dependencies (dbt-core, dbt-duckdb, FastAPI, uvicorn, typer, rich, pydantic, pyyaml, duckdb). Defines the `stellar` CLI entry point. Used by both `uv sync` and `pip install -e .`.

### `setup.sh`
One-command install script. Detects `uv` (preferred) or falls back to `pip`. Installs Python deps, frontend deps (`npm install`), and initializes Level 1. Checks for Python 3.10+ and Node.js 18+.

### `dev.sh`
Starts the game. Adds `~/.local/bin` to PATH (for Codespaces uv), kills stale processes on ports 8000/3000, resets game state, starts both the FastAPI backend and Next.js frontend using `concurrently` with `--kill-others`.

### `uv.lock`
Lock file generated by `uv sync`. Pins exact dependency versions for reproducible installs.

## `dbt_project/` — The real dbt project

Working directory the player edits. Files get wiped and rewritten by the level loader on every level switch.

### `dbt_project.yml`
dbt project configuration. Sets project name (`stellar_pipeline`), paths for models, seeds, tests, snapshots, and target output.

### `profiles.yml`
dbt connection profile. Points at a local DuckDB file (`stellar.duckdb`). One thread, dev target.

### `seeds/raw_shipments.csv`
Source data for shipments. Overwritten by each level with level-specific data (Level 1: 5 clean rows, Level 2: 6 rows with NULLs and loaded_at, Level 3: adds UNKNOWN_TYPE cargo, Level 4+: adds updated_at).

### `seeds/raw_planets.csv`
Source data for planets. 5 rows including Null Meridian (NM-00) — uncharted, not a Federation member. Same across all levels.

### `models/sources/federation_sources.yml`
dbt source definition. Points at the seed tables in the `main` schema. Overwritten by levels that need freshness config.

### `models/staging/stg_planets.sql`
Locked reference model. Shows the CTE staging pattern. Present in every level as a read-only example.

### `models/staging/stg_shipments.sql`
Player-editable staging model. Starts as a skeleton in Level 1, carried forward with solutions in later levels.

### `models/marts/fct_trade_routes.sql`
Player-editable mart model. Placeholder in Level 1, pre-filled in later levels.

### `models/marts/fct_voss_investigation.sql`
Level 6 investigation model. Player builds the VOSS investigation query here.

### `macros/flag_suspicious.sql`
Level 6 macro file. Player defines a reusable Jinja macro here.

### `snapshots/` (created by Level 5)
Not committed to the repo. Created by the level loader when Level 5 starts. Player writes YAML snapshot definitions here.

## `backend/` — FastAPI API layer

Thin HTTP wrapper around the game engine. All endpoints return JSON.

### `__init__.py`
Empty. Package marker.

### `server.py`
All API endpoints:
- `GET /api/status` — game state, objectives, pending narratives (clears pending after delivery)
- `POST /api/start/{level_id}` — initialize a level (wipes models/macros/snapshots, writes files, clears state)
- `POST /api/run` — seed + run models, check objectives, fire narratives
- `POST /api/test` — seed + run tests, check objectives, fire narratives
- `POST /api/build` — seed + build (run + test in dependency order), check objectives
- `POST /api/snapshot` — seed + run snapshots, check objectives, fires SNAPSHOT_RUN event
- `POST /api/reset` — restart current level (clears XP, badges, completed_levels for that level)
- `GET /api/files` — list editable files (models/, macros/, snapshots/)
- `GET/PUT /api/files/{path}` — read/write files (rejects `..` traversal, absolute paths, locked files)
- `GET /api/sources` — list seed CSV files with row counts
- `GET /api/sources/{name}` — preview source data (DuckDB query or CSV fallback), with real total row count
- `GET /api/preview/{model}` — query a built model's results from DuckDB
- `GET /api/manifest` — DAG nodes and edges from manifest.json (excludes seeds/tests, includes sources)
- `GET /api/levels` — list available levels with completion status
- `GET /api/hints/{id}` — get hint text for an objective

### `serializers.py`
Converts game engine objects to JSON-serializable dicts. Handles ActionReport, GameState, objectives tuples, NarrativeEvent.

## `stellar_dbt/engine/` — Core game logic

### `__init__.py`
Empty. Package marker.

### `game_engine.py`
Central orchestrator. Static methods:
- `start_level(id)` — applies level files, clears state + completed_levels for that level, fires LEVEL_START
- `run()` — seed+run, checks objectives, fires per-objective and run events, handles level completion
- `test()` — seed+test, checks objectives, fires test events and per-objective events
- `build()` — seed+build (run+test combined), fires both run and test events
- `snapshot()` — seed+snapshot, fires SNAPSHOT_RUN event, checks objectives
- `check_objectives()` — shows current state without evaluating
- `status()` — returns state + objectives for display

Key behaviors:
- Objectives evaluate only on `run`/`test`/`build`/`snapshot`, not on `start`/`check`/`status`
- `all_models_pass` is gated on all other objectives being complete first
- Per-objective events (`OBJECTIVE_{id}_COMPLETE`) trigger narrative beats
- Hardcode detection only fires when the checker finds an actual `schema.table` pattern (not on empty files)

### `dbt_runner.py`
Wraps subprocess calls to the dbt CLI:
- `run()` — seed then run
- `test()` — seed then test
- `build()` — seed then build
- `snapshot()` — seed then snapshot
- `seed()`, `compile_project()`, `source_freshness()`

Auto-finds the dbt binary in the current venv.

### `artifact_reader.py`
Parses dbt output files:
- `target/run_results.json` — model pass/fail, test pass/fail/error
- `target/manifest.json` — nodes, sources, dependencies (for DAG)

Test failures include both `fail` and `error` statuses.

### `objective_checker.py`
Evaluates objective check conditions. Returns `CheckResult(passed, reason)`.

**File-content checks** (no dbt run needed):
- `has_ref_call` — checks for `{{ ref('model') }}` in active code
- `file_contains` — regex on full file content
- `file_contains_active_sql` — regex on SQL with comments stripped (includes near-miss detection for typos)
- `no_hardcoded_refs` — ensures no `schema.table` after `FROM` or `JOIN`
- `has_test` — finds test definition in YAML (skips target/ directory)
- `has_freshness_config` — finds freshness block in YAML (skips target/)
- `has_column_alias` — regex-based alias extraction (used as fallback, most checks moved to DuckDB)

**DuckDB result checks** (require dbt run):
- `duckdb_columns_exist` — verifies columns exist in model output, optionally with type checking
- `duckdb_column_values` — runs a SQL query that should return 0 violations
- `duckdb_row_count` — checks row count with optional WHERE condition
- `duckdb_column_exists` — single column existence check
- `snapshot_ran` — checks that a snapshot table exists in DuckDB

**Artifact checks**:
- `all_models_pass` — all models in run_results succeeded
- `model_passes` — specific model succeeded
- `tests_ran_with_failures` — tests ran and at least one failed/errored

### `narrative_engine.py`
Matches game events against triggers. Returns messages sorted by priority (high → normal → low). Tracks fired triggers to prevent duplicates.

### `state_manager.py`
Reads/writes `.stellar_state.json`. Tracks: current level, XP, badges, completed objectives per level, fired triggers, run/test counts, pending narratives.

### `_sql_helpers.py`
Regex-based column alias extraction. Used by `has_column_alias` check as a fallback.

## `stellar_dbt/levels/` — Level definitions

### `__init__.py`
Empty. Package marker.

### `loader.py`
Loads level YAML and applies to the dbt project. `apply_level()`:
1. Clears `target/`, DuckDB file, `models/`, `macros/`, `snapshots/` directories
2. Writes base files (stg_planets, default sources YAML)
3. Writes level-specific seed files
4. Writes level-specific initial files (models, macros, snapshots, YAML configs)

### `level_01.yml` — "First Day at the Federation"
Teaches: staging models, `source()`, `ref()`, column renaming/casting/cleaning, joins, GROUP BY aggregation, DAG build order, 1:1 source-staging pattern.
10 objectives. Result-based DuckDB checks validate actual model output (columns, types, values).

### `level_02.yml` — "Something's Wrong with Kepler-7b"
Teaches: `not_null` and `unique` tests, `dbt test` command, `dbt build` (combines run+test+seeds+snapshots), source freshness monitoring.
4 objectives. Introduces the `dbt build` concept via narrative after first test.

### `level_03.yml` — "The Smuggler's Ledger"
Teaches: model and column descriptions in YAML, `accepted_values` tests, dbt docs.
6 objectives. Seed data includes an UNKNOWN_TYPE cargo that tests should catch.

### `level_04.yml` — "The Refresh Crisis"
Teaches: `materialized='incremental'`, `unique_key`, `is_incremental()` filter, `{{ this }}` reference.
5 objectives. Seed data includes `updated_at` column.

### `level_05.yml` — "The Time Ledger"
Teaches: dbt snapshots using modern YAML syntax (not old Jinja blocks), `strategy: timestamp`, `unique_key`, `relation:`, `dbt snapshot` command.
5 objectives. Uses `snapshot_ran` check that verifies the snapshot table exists in DuckDB.

### `level_06.yml` — "The Clean Handoff"
Teaches: Jinja macros (`{% macro %}` / `{% endmacro %}`), reusable logic, CASE WHEN, calling macros from models.
7 objectives. Resolves the VOSS storyline with a 5-part epilogue (R0-B3RT reveals the smuggling operation, VOSS speaks for the first and only time).

## `frontend/components/`

### `StartMenu.tsx`
Animated title screen. Typewriter text crawl with sci-fi backstory, starfield effect, "BEGIN MISSION" button. Click anywhere to skip.

### `GameShell.tsx`
Main layout. Three-column grid: left sidebar (files + objectives), center (editor + bottom pane), right (narrative + terminal). Manages all state. Calls `/api/start/1` on mount (always starts Level 1 fresh). Handles level switching, file opening with error recovery, save with error surfacing in terminal, keyboard shortcuts (Cmd+Enter for dbt run, Escape to close preview).

### `StatusBar.tsx`
Top bar. Logo, level selector buttons (1-6, color-coded by completion), level title, XP progress bar, badges, reset button (↺), "dbt run" button with loading state.

### `FileTree.tsx`
Left sidebar. Groups files by folder, lock icons for read-only. SOURCE DATA section lists seed tables with row counts — clicking opens DataPreview.

### `ObjectivePanel.tsx`
Left sidebar. Checkbox indicators (▸ current, ✓ done), labels, per-objective "hint" button that toggles hint text on click. No automatic hint display — player must ask for it. Highlights newly completed.

### `CodeEditor.tsx`
Monaco editor. Custom "stellar-dark" theme. Saves on blur and Cmd+S. READ ONLY badge for locked files. Keyed on `filePath` for clean switching (not content hash).

### `DataPreview.tsx`
Source data table. Column headers, NULL in red, voss_flag=1 in amber. Close with × or Escape.

### `TerminalPanel.tsx`
Right sidebar. dbt output with ANSI stripped. Four action buttons: "dbt run", "dbt test", "dbt build", "dbt snapshot". Loading state disables all buttons.

### `NarrativePanel.tsx`
Right sidebar COMMS panel. Codec-style single-transmission view:
- Shows one message at a time with animated signal bars in character color
- Position indicator (e.g., "1/3") and dot navigation
- prev/next buttons for browsing the current batch
- "log" button toggles a compact scrollable history (newest first, click to jump)
- New messages auto-display starting from the first message in the batch
- R0-B3RT is the primary character (green), VOSS appears once in the Level 6 epilogue (white)

### `BottomPane.tsx`
Tabbed pane below editor. DAG tab (lineage graph) and PREVIEW tab (query model results). Model selector buttons are dynamically loaded from the manifest. Refreshes after each dbt action.

### `DagView.tsx`
Pure SVG DAG. Topological layer layout. Sources get dashed borders, models get solid. Colors: green (success), red (error), gray (pending). No external graph library.

### `ResultsPreview.tsx`
Queries DuckDB via `/api/preview/{name}`. Shows data table or "Run dbt run first" message. Handles errors gracefully.

### `LevelComplete.tsx`
Modal overlay. Badge emoji, name, XP earned, "Continue" button.
